# Freebuff 通知适配报告

## 1. 适配范围

把本地 Freebuff（Codebuff 桌面版，Electron 应用）的任务状态通知接入 TapRelay，使手机端弹窗正确显示官方名称、图标与品牌色，并完整覆盖三类信号：**任务完成、任务失败、任务暂停待用户确认**。

Freebuff 安装于 `%LOCALAPPDATA%\Programs\@codebufffreebuff-desktop`，与 Claude/ChatGPT 等 Hook 类 Agent 不同：

- 会话/线程终态持久化在本地 SQLite `desktop-v2.db`，因此与 OpenCode/百度网盘一样采用**数据库变更事件驱动**监控；
- “暂停待用户确认”中等待管理员命令确认（`request_elevation` 权限请求）的信号**不在数据库里**，由 orchestrator 进程内维护，只通过本地 HTTP/SSE `GET /api/events` 推送 `elevation_request` 事件，因此额外增加了 **orchestrator SSE 监听**。

全部为只读被动观察：不修改 Freebuff 配置、不注入进程、不写用户的数据库。

## 2. 信号来源与状态映射

### 2.1 数据库终态（任务完成 / 失败 / 停止）

- 数据来源：`~/.config/freebuff-desktop/projects/<项目名>-<uuid>/desktop-v2.db`（WAL 模式，只读 + 共享缓存打开），`threads` 表。
- 完成信号：`turn_state == "idle"` 且 `last_turn_outcome == "completed"` → `status=completed`。
- 失败信号：`last_turn_outcome == "error"` → `status=failed`，正文取 `harness_state.output.message`（真实示例：`API 欠费`、`The session ended before this response completed.`）。
- 用户停止：`last_turn_outcome == "stopped" / "closed"` → `status=stopped`，**不误报失败**。
- 合并冲突等待：`attention_reason == "merge-conflict"` → `status=waiting`（“Freebuff 需要处理合并冲突”），以 `attention_revision` 参与去重键。
- 项目目录：取 `project_path` 作为 `cwd`；`taskId` 为 `freebuff-<threadId>`。
- 耗时：`last_turn_finished_at - last_prompt_at`（毫秒，与 Claude/OpenCode 一样随通知携带，手机端展示）。
- token 统计：取 `messages` 表最后一个 `assistant` 消息的 `metrics_json.usage.totalTokens`（同一事务中先写 assistant 消息再落 `last_turn_outcome`，故终态可见时 token 已就绪）；与 Claude/OpenCode 同语义，手机端 `tokenCount > 0` 时在耗时左侧展示。无 `messages` 表的旧库退化为 0（不阻断读取）。
- 去重：以线程 id 为键维护基线快照，仅当 `updated_at` 推进且终态从空变为终值时上报；监控器接入时先建立基线，**不重放历史完成记录**。

### 2.2 orchestrator SSE（任务暂停待用户确认）

- orchestrator 每次启动随机分配本地 HTTP 端口，仅打印在 `%APPDATA%\Freebuff\logs\orchestrator-stderr.log` 的 `[orchestrator-ready] {...,"port":N}` 或 `listening on http://127.0.0.1:N` 行；从日志末尾向前解析。
- 连接 `http://127.0.0.1:<port>/api/events` 的 SSE 流，接收 `elevation_request` 事件 → `status=waiting`，正文拼接 `reason` 与截断后的 `command`（“Freebuff 需要你确认：<原因>；命令：<命令>”），`taskId = freebuff-elev-<requestId>`。
- 事件字段已对照 orchestrator 源码确认：`{ type: "elevation_request", request: { id, threadId, command, cwd, reason, createdAt } }`，SSE 帧格式 `data: {json}\n\n`。
- 断线自动重连：15s 轮询重新解析端口并重连；`elevation_resolved` 等其它事件忽略。

### 2.3 手机继续续接（resume）

- 失败/完成卡片的“继续”按钮通过既有 WS control 通道 `{type:"control", action:"agent.resume", source:"freebuff", sessionId, cwd}` 回传，PC `AgentResumeRunner` 分发到 `AgentResumeScripts/resume-freebuff.ps1`。
- `sessionId` 即线程 id（与 `taskId=freebuff-<threadId>` 不同，续接需要原线程 id）；`cwd` 即 `project_path`。
- 当前实现由 `FreebuffApiProxy` 直接调用本地 orchestrator：按 `sessionId/threadId` 串行化请求，必要时 `POST /api/thread/<threadId>/stop`，删除旧的 `state=queued` 项，再以 `{text, projectPath, label:"taprelay-continue", now:true}` 调用 `/queue`。`now:true` 会置顶最新项目、解除暂停并触发执行；发送后还会读取线程快照，确认会话恢复才返回成功。
- 手机连续发送时采用“最新消息替换前序未处理消息”语义；停止、队列清理或恢复状态验证失败均返回失败回执，不把“已写入队列”冒充为已执行。用户文本原样传递，空白输入才使用默认继续提示。

## 3. 名称与图标来源

- 名称统一使用官方产品名 **Freebuff**（`appKey=freebuff`；`codebuff`/`code-buff`/`free_buff` 等别名归一化到同一渠道）。
- 图标取自官方安装目录 `%LOCALAPPDATA%\Programs\@codebufffreebuff-desktop\Freebuff.exe` 通过 `SHGetImageList(SHIL_JUMBO)` 提取的官方 256×256 图标（黑底白色星形 Logo），缩放到 `256x256 PNG`。
- 品牌色取自官方 Logo 主色 `#000000`。
- 白色剪影通知小图标：`ic_stat_freebuff.png`（Android 状态栏）。

## 6. 说明

- `freebuff` 为内置保留键，与 `claude`/`codex`/`opencode` 一致，不通过 `/apps/register` 注册（避免被当成未知应用重复注册或覆盖内置元数据）。
- 监控器仅在 Freebuff 进程运行时启用通知，进程退出自动暂停、重启自动恢复；数据库发现结果持久化到 `%LOCALAPPDATA%\LanNotify\freebuff-db-paths.json`，Freebuff 未运行时重启 TapRelay 也能立即接回已知库。
- 用户主动停止（`stopped`/`closed`）映射为“已停止”，符合“不把用户取消误报为失败”的适配约束；`error` 终态必然携带失败原因正文，不静默丢弃。
- Freebuff 已接入“手机继续”：Android 通过统一 `session.send` 控制通道发送，PC 由 `FreebuffApiProxy` 调用本地 orchestrator；`sessionId` 保持原线程 ID，完成/停止后仍可主动续接。
- “暂停待用户确认”有两类独立信号源：合并冲突写数据库（`attention_reason`）、管理员命令确认走 SSE（`elevation_request`），两者都映射为 `status=waiting`，手机端同一渠道展示。
- 耗时与 token 现在对所有智能体统一携带：Claude/Claude Haha/OpenCode/Freebuff 自带终态 usage，Codex（ChatGPT）按轮累计 `token_count` 事件的 `info.last_token_usage`，DeepSeek Harness 按轮累计 `assistant/chunk` 的 usage；ZCode/Doubao/WorkBuddy/Trae 的日志不含可靠用量，`tokenCount` 正确保持 0（手机端不展示），不伪造。

## 7. 历史变更：曾移除手机"继续"指令（2026-08-22）

这段只保留当时的历史状态：旧版续接脚本和 `agent.resume` 控制通道曾被移除，因此报告中原 §2.3 的脚本描述不能作为当前实现依据。后续项目重新启用了统一 `session.send` 控制通道。

2026-09-12 当前 Freebuff 续接由 `pc-app/FreebuffApiProxy.cs` 负责，使用本地 orchestrator API，不修改 Freebuff 配置、不注入进程。它会按线程串行化请求，停止当前回合、删除旧的 queued 项，并以 `now:true` 提交最新文本；之后读取线程快照确认已恢复执行，失败时返回失败回执。具体根因、协议证据和回归结果见项目问题记录 P098。
