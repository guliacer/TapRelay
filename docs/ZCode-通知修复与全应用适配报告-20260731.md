**未达到或不能宣称完成的验收项：**

因此，本轮可判定为：**核心缺陷已修复，Windows + 当前账号 + Android 应用接收链路验证通过；跨平台、跨权限、三类硬件及被系统关闭的通知渠道仍待补充验收。**

## 2. 核心问题与修复

### 2.1 ZCode 日志监听断点

原有监听器包含 ZCode 日志目录和 `ProcessZCodeLine(...)`，但支持文件判断未包含 ZCode CLI 的 `.jsonl`，导致文件变化在解析前被过滤。

已完成：

1. 新增统一路径解析 `AgentLogPaths.cs`。
2. 新增独立事件解析 `AgentCompletionEventParser.cs`。
3. ZCode CLI `.jsonl` 正确进入监控。
4. 路径先规范化为 `/`，覆盖 Windows、macOS、Linux 风格路径。
5. `turn.completed`、`turn.failed` 分开处理。
6. `cancelled/canceled` 不再误报为 failed。
7. 优先使用 `turnId`；缺失时使用 `sessionId:timestamp`。
8. 排除 ZCode Desktop `[repoWiki] ... task_complete ...` 假阳性。
9. Desktop 结构化日志可读取 `workspacePath/workspaceKey/cwd`。

### 2.2 全应用服务端去重唯一性

- Trae：任务 ID 改为 `sessionId:completionToken`，token 优先取 `turn_id/request_id/message_id/timestamp`，最后回退日志行 SHA-256。
- TRAE SOLO：完成/失败使用 `sessionId:agentMessageId`，等待确认使用 `sessionId:planItemId`。
- ZCode：使用每轮 `turnId`，避免同一 session 的连续任务被 15 秒去重窗口吞掉。

### 2.3 Android 丢失任务唯一 ID

原 Android 数据模型只保留 `type/content/time/status/source`，默认 ID 为 `time|type|content`。同一秒、同文案任务会产生相同消息 ID，并可能覆盖系统通知或批量标记。

已完成：

- `NotifyMessage` 新增 `taskId`、`cwd`。
- WebSocket payload 读取 `taskId`、`cwd`。
- SharedPreferences 保存与恢复 `taskId`、`cwd`。
- 新消息 ID 优先使用 `source|status|taskId`。
- 旧数据无 `taskId` 时继续回退 `time|type|content`。
- 新增旧数据兼容、唯一 ID、序列化往返测试。

### 2.4 Windows 免 Runtime 发布

统一打包脚本已从 framework-dependent 调整为 self-contained：

```json
{
  "configuration": "Release",
  "runtime": "win-x64",
  "selfContained": true,
  "singleFile": true,
  "output": "W:\\TapRelay\\pc-app\\publish"
}
```

正式入口：

```text
W:\TapRelay\pc-app\publish\TapRelay.exe
```

重大调整前备份：


| Android 权限 | 应用接收和本地持久化 | 通知运行时权限、厂商后台策略、用户关闭渠道不能静默绕过 | 需遵守系统授权模型 |

### 关于“任意用户点击即用，无需手动配置权限”

Windows self-contained 包已经消除 .NET Runtime 前置依赖，但以下系统约束不能通过应用静默绕过：

- Windows 防火墙首次允许局域网监听可能需要系统授权。
- Android 13+ 的通知权限需要用户授权。
- 悬浮窗、全屏提醒、忽略电池优化属于 Android 特殊权限，需要用户明确授权。
- 用户主动关闭通知渠道后，应用不得自行恢复该渠道。

因此该验收标准只能在“系统已允许必要权限”的前提下实现，不能合规地保证所有新设备完全零授权操作。
