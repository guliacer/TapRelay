# 核心铁律与避坑

## 适用范围
本文件适用于局域网任务通知系统的全局行为边界、性能红线、安全取舍、运行方式与常见 Anti-Patterns。

## 规则条目

### R1: 纯局域网边界
**断言**：默认任务通知链路只使用 PC 与 Android 手机所在网络；不得引入公网服务器、云消息服务、外网回调或第三方 SaaS 转发通知。用户明确要求的 ComfyUI 工作流操作也必须经 TapRelay `1122` 本机服务转发，不能另开手机可见端口或云端通道。
**例外（用户主动配置的隧道优先）**：允许用户在网络设置中配置公网隧道（如 Cloudflare Tunnel）作为**默认连接地址**——二维码主地址为 `wss://<域名>`（443，跨网络稳定连接优先），局域网 `ws://<IP>:1122` 作为兜底候选，仅当隧道不可达时按序连接；隧道只透传 WebSocket 到本机 `1122`，不得承载消息存储、离线补发或云服务。
**自动检测（用户零配置）**：软件启动时自动检测本机已配置的内网穿透/虚拟局域网工具，把可用公网入口自动加入二维码候选（无需用户填写任何设置）。已支持：
- **Cloudflare Tunnel**（cloudflared）：读取 `config.yml`（用户目录 + LocalSystem 服务目录）ingress → `wss://<域名>`
- **frp**（frpc）：读取 `frpc.toml`（v0.52+）/ `frpc.ini`，http/https 代理 → `ws/wss://<域名>`，tcp 代理 → `ws://<server_addr>:<remote_port>`
- **ngrok / cpolar**：读取 `ngrok.yml` / `cpolar.yml`，绑定 hostname → `ws/wss://<域名>`，tcp remote_addr → `ws://<remote_addr>`
- **Tailscale / ZeroTier**：检测虚拟网卡 IP → `ws://<VLAN-IP>:1122`（手机需装同一工具）
- 候选顺序：手动配置 → 自动检测公网隧道 → 虚拟局域网 → 局域网 IP；新工具接入只需在 `TunnelDetectorRegistry.Detectors` 注册一个检测器。
**首次使用傻瓜式（零配置铁律）**：任何需要用户手动完成的设置都必须要么自动化、要么给出引导——服务启动自动执行、端口默认 1122、隧道自动检测、Windows 防火墙自动放行（`FirewallHelper`：启动服务时检测入站 TCP 规则，缺失则 UAC 提权自动添加，用户取消时日志给出可复制命令）、开机自启动菜单化（`AutoStartHelper`，HKCU Run 键）；Android 端系统级权限（通知/电池/悬浮窗/无障碍/自启动）通过权限检测页引导跳转，不阻塞首次连接。
**示例**：
```text
合规链路:
http://localhost:1122/send
ws://192.168.1.100:1122

允许用途:
npm install
Gradle 依赖下载

不允许作为业务链路:
https://api.example.com/push
Firebase Cloud Messaging
Telegram Bot API
```
**违规特征**：通知必须依赖公网可达；服务端向外部 API 转发任务内容；Android 客户端登录云账号才能收通知。

### R2: 端口不可漂移
**断言**：服务端 HTTP 与 WebSocket 必须共用端口 `1122`；不得恢复设计稿旧端口 `9527`，不得为 HTTP 和 WebSocket 分配两个端口。
**示例**：
```js
// W:\TapRelay\notify-server\src\config.js
export const HOST = "0.0.0.0";
export const PORT = 1122;
```
**违规特征**：代码中出现 `listen(9527)`；Android 默认地址为 `ws://<ip>:9527`；`POST /send` 使用 `1122` 但 WebSocket 使用 `1123`。

**ComfyUI 手机控制复用端口**：ComfyUI 手机页只能挂在 TapRelay 的 `http://<PC-LAN-IP>:1122/comfy` 下。PC 内部控制台必须绑定 `127.0.0.1` 的临时端口，并由 TapRelay 负责启动、代理和退出清理；该端口不得写入二维码或提供给手机直连。

### R3: 不擅自加入鉴权
**断言**：当前版本明确不需要认证、登录、token、HMAC、配对码或设备绑定；若未来要加入鉴权，必须先修改本规则文件和 `06-通信与数据获取规范.md`。
**示例**：
```http
POST /send HTTP/1.1
Host: localhost:1122
Content-Type: application/json

{"message":"已完成鉴权模块重构并通过 12 项测试","source":"example-agent","status":"completed","taskId":"task-20260822-001","taskLog":"已完成鉴权模块重构并通过 12 项测试"}
```
**违规特征**：要求请求带 `Authorization`；Android 首次连接必须扫码配对；服务端拒绝无 token 的局域网请求。

### R4: 手动运行优先
**断言**：PC 端默认只提供手动启动方式，正式入口固定为 `W:\TapRelay\pc-app\publish\TapRelay.exe`；不得默认注册 Windows Service、计划任务、开机自启或要求用户启动 `.bat` 文件。`bin`/`obj` 只是构建缓存，不作为用户运行入口。
**示例**：
```powershell
W:\TapRelay\tools\package-pc.ps1
W:\TapRelay\pc-app\publish\TapRelay.exe
```
**违规特征**：安装阶段自动执行 `New-Service`、`schtasks /Create` 或写入启动目录；恢复 `notify-server\start.bat` 作为正式入口；从 `bin\Debug`、`bin\Release` 或临时 `publish-*` 目录长期运行；未询问用户就修改系统级自启配置。

### R5: 推送优先，禁止轮询替代
**断言**：Android 收消息必须通过 WebSocket 长连接推送；不得用 Android 定时轮询 `GET /messages` 替代 WebSocket。
**示例**：
```kotlin
val request = Request.Builder()
    .url("ws://192.168.1.100:1122")
    .build()
okHttpClient.newWebSocket(request, listener)
```
**违规特征**：Android 每 5 秒请求一次 `GET /messages`；服务端维护待拉取队列作为主要通知机制；App 关闭后只能靠手动刷新收消息。

### R6: 服务端不保存业务历史
**断言**：`notify-server` 与 PC 端内置服务只做内存广播与连接管理，不得把消息持久化到文件、SQLite、Redis 或云端；历史消息只允许由 Android 本地保存。
**示例**：
```js
const payload = createMessage(message);
for (const client of clients) {
  if (client.readyState === WebSocket.OPEN) {
    client.send(JSON.stringify(payload));
  }
}
```
**违规特征**：服务端创建 `messages.db`、`history.json`、Redis 连接或消息查询 API；重启服务端后还能返回历史消息。

### R7: PC 托盘退出语义固定
**断言**：PC 端点击窗口关闭按钮必须隐藏到系统托盘并保持 `1122` 服务运行；只有点击托盘菜单 `退出软件` 才允许停止服务并结束进程。**"隐藏"与"退出"是两件事**：隐藏路径不得触碰服务，退出路径则必须满足 R11（进程必死）。
**示例**：
```csharp
protected override void OnFormClosing(FormClosingEventArgs e)
{
    if (!_exitRequested && e.CloseReason == CloseReason.UserClosing)
    {
        e.Cancel = true;
        HideToTray();
        return;
    }

    // 到这里已确定要退出：先武装看门狗，后面每一步清理都可能卡住（见 R11）。
    ArmExitWatchdog();
    _trayIcon.Visible = false;
    _server.StopAsync().GetAwaiter().GetResult();
    base.OnFormClosing(e);
}
```
**违规特征**：点击窗口 X 直接退出进程；隐藏窗口时同时调用 `StopAsync()`；托盘菜单缺少 `退出软件`；退出分支未调用 `ArmExitWatchdog()`（违反 R11）。

### R8: 只发即时通知，不做离线补发
**断言**：通知语义固定为"即时送达"：广播时没有 WebSocket 客户端在线（`sentClients=0`）即视为该消息已丢弃，不得引入待发队列、离线缓存、重连补发或未送达重试机制。
**示例**：
```csharp
// 合规: 无客户端时只记录日志，不入队
Log("broadcast source=" + payload.source + " sentClients=" + sentClients);

// 违规: 暂存待手机重连后补发
if (sentClients == 0) { _pendingQueue.Enqueue(payload); }
```
**违规特征**：服务端出现 `pending`、`backlog`、`outbox`、`retryQueue` 等待发结构；Android 重连后服务端重放期间积压的消息；为"不丢消息"而放宽 R6 的持久化边界。
**背景**：2026-07-30 明确的产品决策。手机被 ColorOS HANS 冻结时会离线（见 `09-问题与优化记录-内容.md` P016），补发能减少漏通知，但会引入服务端状态与持久化需求、与 R6 冲突，且迟到的"任务已完成"提醒没有价值。因此选择保持链路无状态。

### R9: PC 端先构建校验再自动替换、失败恢复，不询问用户
**断言**：需要重新构建 PC 并让改动生效时，必须执行 `W:\TapRelay\tools\package-pc.ps1`。脚本先在既有 `pc-app\obj\package-staging` 完成 Release build/publish，校验 EXE 和匹配的 portable PDB；构建失败保持旧服务运行。随后在 `pc-app\publish\backups` 建立临时恢复快照，仅停止固定发布路径的进程，替换文件、校验哈希、后台启动并验证进程及 `/health`。替换失败恢复旧包；原本运行时须重启并验证。成功后删除临时快照，只有显式 BackupName 才保留成功备份。正式运行入口始终是 `pc-app\publish\TapRelay.exe`，全程无需征求用户同意。
**示例**：
```powershell
# 合规：先构建校验，再替换固定默认目录并自动重启
W:\TapRelay\tools\package-pc.ps1

# 仅重大调整前需要保存旧版时显式创建备份
W:\TapRelay\tools\package-pc.ps1 -BackupName "before-major-protocol-change"

# 正式运行入口始终不变
W:\TapRelay\pc-app\publish\TapRelay.exe
```
**违规特征**：绕过脚本使用任意发布目录；编译前停止旧服务；无快照直接清空发布文件；复制或健康检查失败后未恢复；打包成功没有重启固定路径程序；缺失匹配 PDB；常规成功更新积累临时备份。
**背景**：2026-07-30 用户明确授权 PC 端重新打包自动停-建-启；2026-07-31 进一步明确所有常规 PC 打包产物统一进入固定默认目录，重大调整备份只能位于该目录的 `backups` 子目录，以消除版本散落和运行入口不一致。
**环境说明（不改变本规则的强制流程）**：`tools\package-pc.ps1` 是正式入口，但它**只能在 PowerShell 通道运行**；在受限沙箱里 PowerShell 通道的 `dotnet` 起不来、`schtasks.exe` 在黑名单、`cmd.exe` 被拦，此时改用**等价的 Bash 实现** `tools\deploy-pc-bash.sh [标签]`——它按同样的顺序执行 publish → 快照备份 → 停进程 → 替换 → build-info → 裁剪至 5 个备份 → 清 staging，每步回算 SHA256。该脚本**不负责启动**，启动另用 `tools\run-pc.sh`（先退旧实例再启动，见 R11）。两者都是"先构建校验再替换、失败恢复、不询问用户"，符合本规则；不要因为 ps1 跑不动就绕过校验直接复制文件。

### R10: 推送 GitHub 前必须检查 CPU 与内存占用
**断言**：任何向 GitHub 推送（`git push`）之前，必须先检查本机运行中的 `TapRelay.exe` 进程的 CPU 与内存占用；只有当 CPU 5 秒增量 ≤ 0.5 秒（即 ≤10% 单核）且工作集 ≤ 600MB 时才允许推送；任一指标超标时必须先定位并修复占用问题（优先复用 `09-问题与优化记录-内容.md` 中已收录的 CPU 忙循环/内存根因），禁止带着高占用直接推送。
**示例**：
```powershell
# 合规：推送前先执行一次检查，两项指标均低于阈值才允许 git push
powershell -NoProfile -Command "$p = Get-Process -Name TapRelay | Where-Object { $_.Id -ne $PID }; $a = $p.TotalProcessorTime.TotalSeconds; Start-Sleep -Seconds 5; $p.Refresh(); $cpu = $p.TotalProcessorTime.TotalSeconds - $a; Write-Host ('CPU5s=' + [math]::Round($cpu,2) + 's  Mem=' + [math]::Round($p.WorkingSet64/1MB,1) + 'MB')"
# 判定：CPU5s <= 0.5 且 Mem <= 600 才推送；否则先排查再推送

# 违规：跳过检查直接推送；或 CPU5s > 0.5 / Mem > 600 仍推送
git push
```
**违规特征**：未执行 CPU/内存检查就 `git push`；CPU 5 秒增量超过 0.5 秒或工作集超过 600MB 时仍推送；明知存在忙循环（如 `Application.Idle` 内无条件 `Invalidate()` 导致 UI 线程 100% CPU）或内存泄漏仍提交并推送。
**背景**：2026-08-19 用户要求。PC 端曾出现 `LogScrollBar.Recalculate()` 在 `Application.Idle` 中被高频调用且末尾无条件 `Invalidate()`，产生持续 `WM_PAINT` 消息形成 UI 线程 ~95% 单核满载；修复后稳态 CPU 5 秒增量约 0.14 秒、内存约 130MB。推送前检查用于防止高占用版本流入 GitHub。

### R11: 退出必须做到"进程必死"，端口随进程退出释放
**断言**：PC 端**每一条**退出路径（托盘菜单 `退出软件`、新实例接管 `ExitForNewInstance`、窗体关闭 `OnFormClosing`）都必须**确定性地结束进程**；不得把"退出"押在"清理链路一定走完"上。监听端口 `1122` 由操作系统在**进程退出时**释放，因此"进程一定死"就是"退出即解除占用"的唯一保证——**不得**把端口释放当成需要单独处理的步骤：不需要 `SO_REUSEADDR`，也不需要退出前主动解绑 socket。
**具体要求**：
1. 每条退出路径在开始清理**之前**必须调用 `MainForm.ArmExitWatchdog()`。看门狗是 `IsBackground = true` 的独立线程，用 `Interlocked` 保证只武装一次（三条退出路径会相互嵌套：托盘退出 → `Close()` → `OnFormClosing`），到点强制 `Environment.Exit(0)`；它自身落盘诊断日志的等待也必须有上限（`ExitWatchdogFlushMilliseconds`）。
2. `NotifyServer.StopAsync` 必须保留 `Task.WhenAny` 硬上限：优雅停止 `StopHardCeilingMilliseconds = 1000`、`host.Dispose()` `HostDisposeCeilingMilliseconds = 400`。
3. 退出路径中等待后台清理的超时必须 **≥ `StopAsync` 的自身上限**（现为 `ExitTrayStopWaitMilliseconds = 1600`）。否则超时后 `Close()` 会走进 `OnFormClosing` **再调一次** `StopAsync`（此时 `_host` 尚未置空），总耗时翻倍并撞上看门狗。
**示例**：
```csharp
// 合规：用 WhenAny 给"不遵守 CancellationToken"的 StopAsync 兜底
var gracefulStop = host.StopAsync(stopToken.Token);
var winner = await Task.WhenAny(gracefulStop, Task.Delay(StopHardCeilingMilliseconds));
if (!ReferenceEquals(winner, gracefulStop))
{
    Log("服务优雅停止超过硬上限，直接强制释放（" + StopHardCeilingMilliseconds + "ms）");
}

// 合规：任何退出路径都先武装看门狗，最后无条件 Environment.Exit
private void ExitForNewInstance()
{
    _exitRequested = true;
    ArmExitWatchdog();
    try { _server.StopAsync().GetAwaiter().GetResult(); }
    catch { /* 退出阶段吞掉所有异常，确保进程一定能结束 */ }
    finally { Environment.Exit(0); }
}

// 违规：把"进程必死"押在清理一定走完上（token 不生效时会永久挂住）
await host.StopAsync(cancellationToken);
Environment.Exit(0);
```
**违规特征**：`await host.StopAsync(token)` 没有 `WhenAny`/超时兜底；丢弃 `StopAsync` 返回的 Task 不等待；新增退出路径未调用 `ArmExitWatchdog()`；退出路径的清理等待短于 `StopAsync` 自身上限（会触发二次 `StopAsync`）；为"看起来更优雅"去掉硬上限或看门狗；**因为某次没复现挂死就删掉上限与看门狗**；改用 `SO_REUSEADDR` 或退出前主动解绑来"解决"端口占用。
**背景**：2026-10-12 用户报「退出时端口还被占用」。取证：`%LOCALAPPDATA%\LanNotify\pc-server.log` 停在 `开始停止服务，已立即中止 0 个手机客户端连接`，之后既无 `服务优雅停止超时` 也无 `服务已停止，耗时 …ms`；而 `Get-NetTCPConnection -LocalPort 1122 -State Listen` 在约 667ms 时已为空，PID 22032 仍以 137MB 滞留——**真正没退的是进程，不是端口**。根因：`Host.StopAsync(CancellationToken)` 在等待 `ApplicationLifetime` 停止信号与托管服务停止时**不完整遵守**传入的 token，会**永不返回且不抛异常**；而当时三条退出路径都没有任何上限，返回值也被丢弃。修复后实测端口释放 967ms、进程消失 1148ms（此前为"永不"）。**挂死是间歇性的**：同一次会话里另一次接管退出只用 4ms，故"这次没复现"不构成删除兜底的理由。三条路径均已无头验收：接管退出、托盘退出（`--exit-probe`，625ms）、带 3 个在线 WebSocket 客户端退出（此时才真正走到 `AbortConnectedClients`）。相关：R2（端口所有权与固定策略在 `NetworkSettingsStore.PinPort`）、R7（托盘退出语义）、R9（构建与替换流程）。
